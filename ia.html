  • 🦊 Le Renard — the on-board technical assistant. Answers boat questions grounded in your documentation (manuals, videos, schematics), citing sources. Skipper-only.

② Alignement avec les standardsAlignment with standards

Wang'ap est une application personnelle/familiale qui utilise des services d'IA tiers (elle n'en produit pas). Une certification ISO/IEC 42001 (système de management de l'IA) vise des organisations qui commercialisent de l'IA — elle serait disproportionnée ici. En revanche, l'app s'aligne volontairement sur les principes de ces cadres :

Wang'ap is a personal/family app that consumes third-party AI (it does not build AI). An ISO/IEC 42001 (AI management system) certification targets organisations that ship AI — it would be disproportionate here. Instead, the app voluntarily aligns with the principles of these frameworks:

  • ISO/IEC 42001:2023 — système de management de l'IA (le référentiel certifiable).AI management system (the certifiable standard).
  • ISO/IEC 23894:2023 — gestion des risques liés à l'IA.AI risk management guidance.
  • NIST AI RMF 1.0 — cadre de gestion des risques (Govern / Map / Measure / Manage).risk framework (Govern / Map / Measure / Manage).
  • EU AI Act — un assistant documentaire + rédaction relève du risque minimal/limité → surtout des obligations de transparence.a documentation assistant + drafting is minimal/limited risk → mainly transparency duties.

③ Architecture technique — Le Renard (RAG)Technical architecture — Le Renard (RAG)

Le Renard repose sur une architecture RAG (Retrieval-Augmented Generation). Plutôt que de répondre « de mémoire », le modèle reçoit d'abord les extraits pertinents de ta documentation, puis rédige à partir d'eux.

Le Renard is built on RAG (Retrieval-Augmented Generation). Instead of answering "from memory", the model is first given the relevant excerpts of your documentation, then writes from them.

1. Ingestion multimodale & découpage

1. Multimodal ingestion & chunking

Un worker GitHub Actions récupère les fichiers d'un dossier Google Drive. Le texte (PDF via pdfjs, Word via mammoth, Google Docs exportés) est nettoyé (retrait des caractères de contrôle C0/NUL — sinon Postgres refuse l'insertion) puis découpé en chunks d'environ 2000 caractères avec 800 de chevauchement, la coupe se calant sur une fin de phrase (pour ne pas scinder une idée). Vidéos et schémas suivent des chemins dédiés (ci-dessous) mais aboutissent au même index.

A GitHub Actions worker pulls files from a Google Drive folder. Text (PDF via pdfjs, Word via mammoth, exported Google Docs) is cleaned (C0/NUL control chars stripped — Postgres rejects them) then split into ~2000-char chunks with 800 overlap, cutting on sentence boundaries. Videos and schematics take dedicated paths (below) but land in the same index.

2. Vidéos — extraction du son puis transcription

2. Video — audio extraction then transcription

Une vidéo n'a pas de texte : l'information est dans la parole. ffmpeg extrait la piste audio en MP3 mono 16 kHz, découpée en segments de 20 min (l'API de transcription plafonne à 25 Mo / ~25 min). Chaque segment passe chez OpenAI Whisper en mode verbose_json (horodatage par segment de parole) ; les timestamps sont décalés de index × 1200 s pour se recoller sur une timeline continue. La transcription est regroupée en chunks de ~600 caractères portant t_start_sec / t_end_sec. Résultat : la source cite « voir vidéo … à 4:32 » et le lien ouvre la vidéo Drive au bon timecode.

A video has no text — the information is in speech. ffmpeg extracts the audio as 16 kHz mono MP3, split into 20-min segments (the transcription API caps at 25 MB / ~25 min). Each segment goes to OpenAI Whisper in verbose_json mode (per-speech-segment timestamps); timestamps are offset by index × 1200 s onto a continuous timeline. The transcript is grouped into ~600-char chunks carrying t_start_sec / t_end_sec. The source then cites "see video … at 4:32" and the link opens the Drive video at that timecode.

3. Schémas — vision Claude

3. Schematics — Claude vision

Un PDF scanné (sans couche texte) est rendu page → image (pdfjs + @napi-rs/canvas), puis décrit par la vision de Claude (composants, numéros de câbles, connexions X→Y, repères de zone). Cette description devient un chunk normal (embeddé + indexé), avec meta.image_url vers l'image — d'où le lien 🔌 qui montre le schéma sous la réponse.

A scanned PDF (no text layer) is rendered page → image (pdfjs + @napi-rs/canvas), then described by Claude vision (components, cable numbers, X→Y connections, zone markers). That description becomes a normal chunk (embedded + indexed) with meta.image_url to the image — hence the 🔌 link that shows the diagram under the answer.

4. Embeddings & stockage vectoriel

4. Embeddings & vector store

Chaque chunk (texte, transcription vidéo ou description de schéma) est transformé en vecteur de 1536 dimensions par OpenAI text-embedding-3-small — une position dans un espace où proximité géométrique ≈ proximité de sens (« préfiltre 5 microns » ≈ « cartouche de filtration », sans mot commun). Stocké dans PostgreSQL + pgvector : colonne embedding vector(1536) (index approximatif IVFFlat/HNSW pour les plus proches voisins) + colonne tsvector (config french, stemming) pour le plein-texte. Les lots d'embeddings sont bornés par budget de caractères (le plafond OpenAI de 300k tokens se calcule mal en caractères/4 pour l'arabe / le CJK).

Each chunk (text, video transcript or schematic description) becomes a 1536-dimension vector via OpenAI text-embedding-3-small — a point in a space where geometric closeness ≈ semantic closeness. Stored in PostgreSQL + pgvector: an embedding vector(1536) column (approximate IVFFlat/HNSW nearest-neighbour index) + a tsvector column (french config, stemming) for full-text. Embedding batches are bounded by a character budget (OpenAI's 300k-token cap is mis-estimated by chars/4 for Arabic / CJK).

5. Recherche hybride (dense + creuse) + RRF

5. Hybrid retrieval (dense + sparse) + RRF

Un seul appel SQL (match_rag_documents) lance deux recherches :

One SQL call (match_rag_documents) runs two searches:

  • Vectorielle (dense) — ORDER BY embedding <=> :q (distance cosinus), top-24 par le sens.
  • Vector (dense) — ORDER BY embedding <=> :q (cosine), top-24 by meaning.
  • Plein-texte (creuse) — sur le tsvector FR, lexèmes reliés en OU ('a' | 'b' | 'c') pour ne pas exiger tous les mots ; classé par ts_rank.
  • Full-text (sparse) — on the FR tsvector, lexemes OR-ed ('a' | 'b' | 'c') so not every word is required; ranked by ts_rank.

Fusion par RRF (Reciprocal Rank Fusion, k=60) — on additionne les rangs (pas les scores bruts, non comparables) :

Merged by RRF (Reciprocal Rank Fusion, k=60) — summing ranks (not raw, incomparable scores):

score = 1 / (60 + rang_vecteur) + 1 / (60 + rang_texte) → garder les 12 meilleurs

Le vecteur apporte le sens, les mots-clés la précision (numéros de pièce, sigles) ; et si l'embedding échoue, le plein-texte porte seul la récupération (résilience).

Vector brings meaning, keywords bring precision (part numbers, acronyms); and if the embedding fails, full-text carries retrieval alone (resilience).

6. Carnet de maintenance — contexte ambiant

6. Maintenance log — ambient context

En plus des extraits récupérés, Le Renard injecte l'état vivant du bord : les 5 dernières entrées de maintenance_logs (titre, catégorie, description, heures moteur, date) sont ajoutées au contexte sous un bloc « MAINTENANCE RÉCENTE » — sans pastille source (ce sont des faits opérationnels, pas de la doc). C'est ce qui permet à Claude de croiser la doc avec le réel (« je ne trouve aucune trace d'entretien récent du dessalinisateur »).

Beyond the retrieved excerpts, Le Renard injects the boat's live state: the last 5 maintenance_logs entries (title, category, description, engine hours, date) are added to the context as a "RECENT MAINTENANCE" block — without a source chip (operational facts, not documentation). This lets Claude cross-check docs against reality ("I find no recent watermaker service").

7. Génération, citations & modèle en direct

7. Generation, citations & live model

Le contexte (extraits + maintenance) part chez Claude avec un prompt strict : citer la source (document + page), ne rien inventer, renvoyer vers un pro pour la sécurité. La réponse est streamée en SSE delta par delta ; les sources (et l'image d'un schéma) arrivent dans un événement séparé, rendu sous la réponse. Le modèle (Haiku / Sonnet) est résolu en direct depuis la liste /v1/models d'Anthropic (le plus récent de la famille), avec repli automatique — donc aucun identifiant de modèle codé en dur ne peut « expirer ».

The context (excerpts + maintenance) goes to Claude with a strict prompt: cite the source (document + page), never fabricate, defer to a pro for safety. The answer is streamed over SSE delta by delta; sources (and a schematic's image) arrive in a separate event rendered under the answer. The model (Haiku / Sonnet) is resolved live from Anthropic's /v1/models list (newest of the family), with automatic fallback — so no hardcoded model id can "expire".
